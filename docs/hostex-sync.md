# Hostex inbound synchronization and repair

Implementation reference, checked against the official Hostex v3 documentation on 2–3 October 2026. The operator supplied a live Pull failure report and UI screenshots, but no authenticated production session or raw Hostex response was available. Fixtures are synthetic. Successful automated checks must not be described as a verified live pull.

## Root causes and corrected flow

The previous adapter expected undocumented property, nested guest and financial fields. It confused Hostex order codes with OTA confirmation codes, defaulted missing money to zero/USD, and spread reservation totals across nights. Updates returned early when dates had not changed. The generic importer inferred collected payments from channel configuration. Property discovery saved metadata without hydrating the mapped property; mapping an already discovered ID could violate uniqueness. Pictures were neither imported nor requested/rendered by property cards. Name matching could link the wrong property. Reservation uniqueness did not include the connected account. Partial failures could advance the successful watermark, and the browser ignored numeric failure counts.

The inbound path is now:

`Channels → Pull now → POST /api/v1/channels/{account}/pull → ChannelPuller → property discovery → listing/pricing/calendar details → reservation upserts → transaction snapshots → optional messages → resources → refreshed screens and agent context`.

Pull runs synchronously. Its database result records the current stage while running and the completed counts, failures, limitations and coverage afterward. It does not report a queued job as completed. A disconnected browser may need to refresh the Channels page to read the persisted result. Configure the deployment's request timeout for the estate size. An abandoned `running` result never advances the successful watermark; after a hard worker termination its lease expires within two hours of the last stage renewal and can then be retried.

Credentials remain encrypted in `channel_accounts.credentials.access_token`, entered in Channels settings, and are sent using `Hostex-Access-Token`. No new credentials are required in source control. `hostex:probe --raw` now prints nested types with values redacted, not guest records. Provider errors expose safe categories and codes, not raw response bodies.

## Verified sources

- [Properties](https://api-doc.hostex.io/reference/query-properties): Hostex properties and their connected channel listing IDs.
- [Listings](https://api-doc.hostex.io/reference/query-listings): OTA listing identifiers, URL, cover and best-effort cached metadata.
- [Airbnb prices and rules](https://api-doc.hostex.io/reference/get-airbnb-listing-price-and-rules): additional read required for base price, fees and booking rules.
- [Listing calendars](https://api-doc.hostex.io/reference/query-listing-calendars): **POST is a documented read-only query**; dates, prices, inventory and restrictions.
- [Reservations](https://api-doc.hostex.io/reference/query-reservations) and [rate detail meanings](https://api-doc.hostex.io/reference/reservation-rate-details): stay/order/channel identifiers, guest, rate breakdown and order collection records.
- [Transactions](https://api-doc.hostex.io/reference/query-transactions): source income/expense records, separate from local accounting.
- [Rate limits](https://api-doc.hostex.io/reference/rate-limits): errors can be delivered as `error_code: 429` inside HTTP 200.
- [Error codes](https://api-doc.hostex.io/reference/errors): distinguish invalid requests, access, subscription restrictions, rate limits and upstream failures without exposing raw error bodies.

## Follow-up to the operator's failed Pull

The live result confirmed property discovery, dated calendar prices and transactions worked. It reported 78 unreadable images and one reservation request failure; the screenshot showed a cached CAD 60 base price while the local property remained USD 0. The original request error was discarded, so its exact provider cause cannot be recovered from that report.

- The currency guard now checks nonzero pricing overrides scoped to this property, its listings or unit types. Shared rules are evaluated in each property's currency by the existing pricing engine; unrelated rules and zero thresholds must not keep an unpriced property in USD. Real local amounts remain protected. A blocked currency update now makes the Pull partial and gives an actionable issue.
- The main property card uses the persisted base rate. Normal editor fields show imported pricing, fees, arrival times, included guests and instant booking. Money fields name CAD when that is the stored denomination. Source-only details and dated prices are in the editor, instead of expanding the property card.
- The documented image container accepts a plain URL or structured metadata with one unambiguous URL value, without inventing channel-specific field names. HTTP and protocol-relative image links are upgraded to HTTPS and pass the same public URL validation. Ambiguous entries remain unsupported. Repeated failures are grouped; the first usable image becomes the cover when necessary. This is a structural parser, not a claim that the operator's actual image shape has been verified.
- If a broad reservation history request fails because of validation or a server/connection error, it falls back to contiguous checkout windows of at most 180 inclusive days, retaining the configured overall coverage and deduplicating stay IDs. This is a defensive recovery strategy, not a documented Hostex maximum or a confirmed explanation of the live failure. Access, account, missing-resource and rate-limit errors are not retried with different dates. Failures retain safe error codes, categories and requested coverage.
- A legacy booking without a refreshed source snapshot now explains that state once rather than expanding a long list of unavailable amounts. A successful refresh updates the existing reservation and guest, including contact details and OTA confirmation.

The ordinary reservation `paid`, `balance_due`, `expected_payout` and `refunded` fields are unavailable for these imports. Source collections and refund detail lines have their own labels. Guest-facing totals are also unavailable because the stay rate is not a verified guest invoice total. Unknown payment state does not satisfy existing payment checks for releasing private arrival information. An invoice is not synthesized from a Hostex stay rate.

Existing aggregate revenue/owner reporting now refuses selections with missing accommodation amounts, unverified mixed currencies, or previously posted legacy revenue awaiting review. Individual source amounts remain readable. Guest lifetime totals become unavailable when their denomination or inputs cannot be combined accurately. Arrivals reports preserve unknown balances and decline mixed-currency balance totals.

## Source limitations and ownership policy

The documented property/listing response has no stable fields for full listing description, property type, sleeping capacity, bedroom/bed/bath counts, amenities, timezone or narrative house rules. Listing metadata is explicitly best-effort and varies by connection. This implementation does not invent keys for those fields. Existing local values remain. A sanitized live schema is required before supporting richer connection-specific metadata. Image captions/object gallery schemas are likewise not guaranteed; unsupported image entries are reported instead of silently disappearing.

Verified Airbnb guest total, host payout and payout status are not supplied with those meanings by the reservation fields above. They are shown as unavailable. This is a limitation of the documented contract inspected, not a claim that every Hostex plan/connection has been exhaustively tested. Access denials, malformed responses, unsupported metadata and refresh failures are reported separately from documented gaps.

The first explicit property mapping opts its supported fields into source management. Local operational instructions, contacts, owners, documents, amenities and local availability rules stay local. A supported field edited after import is detected by comparison to the last applied value and recorded in `properties.settings.hostex_overrides`. Administrators can also list fields there before the first mapping. Clearing an override requires restoring the last applied value and removing that field from the override list before pulling again. A second source mapping cannot silently take ownership of the same property's content.

Partial omissions retain earlier values; they are not deletion signals. Explicit null financial fields become unavailable, and an explicit detail/fee array replaces the previous array. A cancelled status is a supported explicit state change. There is no documented general tombstone feed here: missing properties, gallery entries or transactions are retained, not deleted. Imported photo captions can be edited locally; source ordering is reapplied on pull. Removing a source photo locally alone is not a permanent source deletion.

Source image URLs can expire or require authentication. Pull refreshes public URLs; failed browser loads show a fallback. There is no server-side image fetch that could attach a Hostex token to an arbitrary host. Authenticated-only images cannot be displayed without a supported source URL.

## Coverage, retries and idempotence

- Collection reads use `offset`/`limit` and reported totals, up to 10,000 rows per collection/window. A truncated or later failed page reports partial coverage while retaining earlier pages. Malformed individual reservations do not discard valid rows.
- Reservations use an explicit **checkout-date** window, by default today minus two years through today plus three years. Hostex does not offer a documented modified-since filter for this query, so each pull rereads the window. `--full` does not mean unlimited history. Account `settings.hostex_reservations_from` and `hostex_reservations_to` can select a different ISO-date window; narrow it if the cap is reached. Changes outside that window require a separate backfill window.
- Transactions default to two years before today through today, split into inclusive windows of at most 366 days. Set `settings.hostex_transactions_from` for earlier history. Hostex interprets transaction dates in its operator timezone; coverage is disclosed and boundary review may require an overlapping day.
- Calendar snapshots cover today through 365 days ahead. Returned days are distinguished from absent days, which are unavailable. Earlier/omitted values inside the coverage window may be retained after partial responses.
- Read requests retry transient/network errors at most twice. Short `Retry-After` values are honored; longer cooldowns are returned as retryable failures, never shortened. Outbound writes are not retried by this change. The only POST in the new inbound path is the documented calendar query.
- A database-backed lease in the existing `cache_locks` table prevents overlapping pulls for the same tenant/account and works with Neon's transaction pooler. It expires after two hours, renews between stages and is released only by its owner; a single stage should fit inside that lease. Database account-row locks also serialize first inserts, mapping/adoption and reservation/message imports. Uniqueness includes account identity. Multi-stay orders are separate reservations sharing an order reference. Inbound discovery preserves paused mappings; it cannot re-enable outbound synchronization.
- A legacy reservation keyed by order is adopted only when account, property and dates agree. Internal reservation/guest IDs survive. Ambiguous legacy associations are reported for review. Guest IDs are preferred to names or masked email matching; without a stable guest ID, the order is the conservative fallback.
- Existing inferred local payment records are preserved with a review warning. Recognized nightly revenue is never rewritten; source mismatches are flagged for accounting review, while unchanged allocations do not trigger a false warning. Unposted legacy nightly estimates can be replaced with verified accommodation allocations. A source reactivation clears stale cancellation timestamps without changing the internal reservation ID.

## Deployment and repeatable repair

1. Back up the production database and deploy this branch using the existing deployment process. Run `php artisan migrate --force`, then rebuild the frontend with `npm ci` and `npm run build` in `frontend`. Clear/rebuild configuration as usual. The new migration adds source snapshots/guest links/photo references, pull progress fields, order references, nullable reservation amounts and account-aware uniqueness. Once source data exists, destructive rollback is refused; use a backup or a forward repair.
2. Set `PMS_OPERATING_CURRENCY=CAD`. New organizations/defaults use CAD. Existing organization base currencies and historical ledger denominations are not mass-relabeled. If the existing organization is wrongly configured as USD, review its historical financial denominations and change the organization setting deliberately; source imports retain CAD/USD/etc. exactly as supplied regardless of that setting.
3. Open Channels, use the existing Hostex connection, verify that **Import bookings** is enabled, and click **Pull now**. Leave outbound availability/rate switches as configured; this repair does not require enabling them.
4. Map each discovered **Hostex property ID** to the correct existing local listing. The mapping reuses the discovered row and immediately applies cached property details, prices and photos. Do not delete and recreate a property. If a record is already mapped, keep that mapping.
5. Click **Pull now** again to import/repair reservations and transaction associations for the mapped property. For an existing mapping, one pull is sufficient. The equivalent repeatable command is `php artisan channels:pull --account=ACCOUNT_ULID --full`. Use the connected account ID, not an organization/property/Airbnb ID. The command exits nonzero for partial failures.
6. Inspect the stage results, coverage and completion time; distinguish last attempt from last successful pull. Resolve reported missing mappings or ambiguous legacy stay identities and retry. A limited/denied endpoint remains visible as a failure instead of advancing the successful watermark.
7. Verify one property against its source: name/address, listing ID/link/status, cover/gallery, base nightly price and one dated calendar price. Inspect one reservation: actual guest, OTA confirmation, separate Hostex stay/order IDs, accommodation and derived nightly average, stay commission, order collections and currencies. Check Financials → Hostex records for source transaction evidence. Do not compare an order collection amount to a single stay balance or treat it as a payout.
8. Pull a second time and confirm the local property/reservation/guest IDs and photo/transaction counts remain stable. Search by the OTA confirmation. Confirm the permitted property agent can read the source references and financial snapshot; unavailable fields should remain unavailable.

Production repair and the final source comparison have **not** been performed in this workspace. No production credentials, guest records or screenshots are included. See the verification report for the automated results.

If creating a property from a discovered listing instead, missing source capacity leaves the new property in draft. Existing Hostex bookings can still be pulled into that mapped draft. Complete the local capacity and other activation requirements before enabling local booking sales.
