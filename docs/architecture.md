# Architecture

Habitat is a multi-tenant property management platform for short-term rentals,
vacation rentals, serviced apartments, boutique hotels and multi-unit
portfolios. This document describes how it is put together and, where a choice
was contentious, why it was made that way.

## The stack

| Layer | Choice |
|---|---|
| Runtime | PHP 8.4 (8.3 is the supported floor), Laravel 13 |
| Database | PostgreSQL 16 |
| Cache, queue, locks | Redis |
| HTTP server | FrankenPHP |
| Admin interface | React 19 + TypeScript, built by Vite, served as static files |
| Formatting | Laravel Pint |
| Tests | PHPUnit against a real PostgreSQL database |

Nothing here is exotic. The interesting decisions are in how the application
code is organised, not in what it runs on.

## A modular monolith

The application is one deployable, divided into domains under `app/Domain`:

```
app/Domain/
  Accounting/      Audit/           Api/             Automation/
  Availability/    Channels/        Documents/       Events/
  Guests/          Integrations/    Listings/        Locks/
  Messaging/       Notifications/   Operations/      Organization/
  OwnerAccounting/ Owners/          Payments/        Platform/
  Pricing/         Properties/      Reports/         Reservations/
  Reviews/         Upsells/         Users/           Webhooks/
```

Each domain holds its own `Models/`, `Services/`, `Enums/`, `Events/`,
`Policies/`, `DataObjects/`, `Exceptions/`, `Listeners/` and `Jobs/`. HTTP
controllers live outside the domains, in `app/Http/Controllers/Api/V1/<area>/`,
and are thin: they authorise, validate, call one service and return a resource.

The domains are separated in code rather than in processes, because the data is
densely joined. A reservation touches the property, the listing, the
guest, the rate plan, the tax rules, the ledger, the owner's agreement and the
cleaning rota — all inside one transaction that must either commit or not. Once
those are separate services, that transaction becomes a distributed one, and
the two hard problems of this product (never double-book, never misstate an
owner's money) become dramatically harder for no benefit at this size.

The domain boundaries are still real. They make the seams visible, and they are
where the cut would be made if part of this ever had to become its own service.

### Cross-domain wiring

Domains do not reach into each other. Where one has to react to another,
`App\Providers\DomainServiceProvider` wires them together:

```php
Event::listen(ReservationConfirmed::class, [ScheduleTurnoverForReservation::class, 'handleConfirmed']);
Event::listen(ReservationCancelled::class, [ManageAccessCodesForReservation::class, 'handleCancelled']);
```

The reservation service does not know operations exists, and operations does
not reach into reservations. Adding a reaction is a line in one provider.

## Multi-tenancy

Every tenant-owned table carries `organization_id`. `TenantContext` is a
request-scoped singleton holding the active organization, and the
`BelongsToOrganization` trait adds a global scope that filters every query and
stamps every insert.

The important part is what this is *not*: it is not an ambient convenience that
can be forgotten. A model with the trait has no unscoped read path except the
explicit `withoutGlobalScope('organization')`, which appears in a handful of
places (provisioning, platform administration, the tenant resolver itself) and
nowhere else. `tests/Security/TenantIsolationTest.php` exists to keep that true.

The tenant is chosen explicitly by the client — an `X-Organization` header —
rather than inferred, because a user may work for more than one company and a
server that guesses will eventually guess wrong.

## Identifiers

Primary keys are ULIDs. They sort by creation time, so indexes stay dense; they
carry no sequence a competitor can count; and they can be generated before
insert, which matters when a record and its ledger entries are written in one
transaction.

Human-facing references are separate and sequential — `HB-000123`, `CLE-00045`,
`EXP-000012` — generated by `SequenceGenerator` with a per-organization row
lock. A sequence stores the prefix it was created with and reuses it, which is
why every kind that needs its own prefix gets its own sequence key. Sharing one
would stamp whichever kind happened to be created first onto all of them.

## Money

`App\Support\Money\Money` is an immutable value object over integer minor
units plus a currency. No float ever touches an amount. Division is explicit:
`allocateEvenly()` and `allocateByWeights()` distribute a sum so the parts add
back to exactly the whole, with the remainder assigned rather than lost.

Money serialises as:

```json
{ "amount": 14500, "currency": "EUR", "formatted": "145.00" }
```

All three, deliberately. `amount` is what a client should compute with,
`currency` is what makes it meaningful, and `formatted` saves every client from
reimplementing minor-unit arithmetic for currencies that do not have two
decimal places.

## Time

Timestamps are stored as `timestamptz` and serialised with their offset
(`BaseModel::$dateFormat` is `'Y-m-d H:i:sP'`). Dates that are calendar facts —
a check-in date, a stay night — are stored as dates.

Operational time is evaluated in the *property's* timezone, not the server's.
"The clean is due at 11:00" means eleven o'clock where the property is.
`tests/Feature/Platform/TimezonePersistenceTest.php` guards the round trip.

## Domain events

Every meaningful change raises an event implementing `DomainEventContract`. One
listener persists it to the `domain_events` table; every other consumer reads
from that stream:

```php
Event::listen(DomainEventContract::class, [RecordDomainEvent::class, 'handle']);
Event::listen(DomainEventContract::class, [RunAutomationForEvent::class, 'handle']);
Event::listen(DomainEventContract::class, [SendEventToWebhooks::class, 'handle']);
```

Registration order is load-bearing rather than cosmetic: the recorder hands the
event the id of the row it wrote, and both automation and webhook delivery cite
that id — automation on every run it creates, webhooks as the deduplication key
in a partial unique index on `webhook_deliveries`. A redelivered job is
therefore harmless.

The consequence is that adding a consumer never requires touching the code that
produces an event, and adding an event makes it automatable and deliverable
without touching either consumer.

## Concurrency

Two places matter.

**Availability.** `AvailabilityEngine::reserve()` opens a transaction, takes
`SELECT ... FOR UPDATE` over the blocking reservations that overlap the
requested window for that property, *then* re-checks availability, then runs the
caller's callback. The lock is coarse — it covers the set any competing booking
would also have to touch — which is exactly why it is correct. Contention is
limited to genuinely competing stays.

**Sequences.** `SequenceGenerator` locks the sequence row for the organization
before incrementing, so two simultaneous bookings cannot receive the same
confirmation code.

## Layering, concretely

```
HTTP request
  → route (permission middleware)
  → controller           authorise, validate, delegate
  → service              business rules, transactions, events
  → model / query        persistence
  ← API resource         shaping, including the honesty flags
```

A controller never contains a business rule, and a model never contains a
workflow. Where a rule is expressed as "the interface should not offer this",
the server enforces it too — hiding a button is a courtesy, not a control.

## The admin interface

`frontend/` is a React SPA in TypeScript, built into `public/app` by a Docker
stage and served by the same process as the API. It authenticates with a bearer
token and names its tenant with the `X-Organization` header.

The types in `frontend/src/api/types.ts` are written against the actual API
resources rather than generated, and every screen shows the provenance flags the
API reports (see [integrations.md](integrations.md)).

## Honesty as an architectural constraint

The platform carries several flags whose only job is to stop the interface
claiming more than the system did:

| Flag | Says |
|---|---|
| `is_simulated` (payment) | No real payment provider processed this |
| `is_collected_by_us` | Whether the money reached our account or a channel's |
| `is_simulated` (sync job) | The adapter that ran this talks to a local simulation |
| `delivery.simulated` (message) | Recorded by a local transport, not actually sent |
| `is_simulated` (access code) | The lock provider is a mock; this opens no door |
| `opens_a_real_door` | Same fact, stated positively where a code is displayed |

These are not debug fields. They are part of the contract, they are surfaced in
the UI, and `DemoSeederTest` asserts that nothing in the demo violates them.
